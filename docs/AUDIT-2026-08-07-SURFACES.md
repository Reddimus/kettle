# Surface audit — 2026-08-07

The five crate audits recorded in `AUDIT-2026-08-07-FULL.md` covered the Rust
source of all ten crates. They did not cover the surfaces *around* that source:
the installer and release scripts, the CI workflows, the packaging metadata and
shell-integration snippets, the documentation's factual accuracy against the
code, Kettle's UI/UX as a product, and consistency between the GUI, the `kettle
ctl` control plane, and the MCP tools.

Forty agents audited those six surfaces in parallel, and every finding was then
handed to a separate agent instructed to REFUTE it. Twenty-three survived; ten
were refuted and are listed at the end so they are not re-investigated.
Severities below are the verifier's corrected values, which in several cases are
lower than the auditor filed.

## Summary

Six surfaces were audited — CI workflows (`.github/workflows/`), install/release scripts (`scripts/`), shell-integration snippets (`shell-integration/`), user-facing docs (`docs/`, `packaging/linux/kettle.1`), the Settings/UI layer (`crates/kettle-ui/`), and the agent-facing ctl/MCP surfaces. 23 findings survived adversarial verification (each was independently re-checked by an agent instructed to refute it): 4 HIGH, 11 MEDIUM, 8 LOW; 11 further claims were refuted and are listed at the end. The dominant theme is **guards that fail open and contracts that outrun the code**: three CI gates cannot turn red (a `rg` that isn't installed, an action whose scheduled leg only files issues, a pwsh step that reports the last command's exit code), two installer/shell paths silently rewrite or destroy state they don't own, and six doc/label surfaces promise behavior the implementation never had. Severities below are the verifier-corrected values; where they differ from the filed value that is noted.

## packaging — shell integration

### HIGH — zsh snippet prints a literal `$(...)` in every prompt and never emits OSC 133;B
- **Where:** `shell-integration/kettle.zsh:38` (mirrored in `docs/SHELL-INTEGRATION.md:136`)
- **Trigger:** Follow the documented `kettle --shell-integration zsh >> ~/.zshrc` on stock zsh. `PS1='%{$(print -Pn "\e]133;B\a")%}'"$PS1"` needs `PROMPT_SUBST`, which is off by default (macOS ships it off; oh-my-zsh/starship set it, which is why this hides).
- **Wrong outcome:** Every prompt renders `$(print -Pn "\e]133;B\a")` — 25 literal characters — before the user's prompt. Inside `%{...%}` zsh counts them as zero-width, so ZLE column arithmetic is off by 25 for the whole line (redraw, backspace at line start, history recall). Confirmed live on zsh 5.9: no `ESC ] 133 ; B BEL` in the byte stream; adding `setopt prompt_subst` makes the same file correct. Scope: only the B mark is lost — 133;A/C/D and OSC 7 come from `print -Pn` in precmd/preexec and still work, so prompt-mark navigation and cwd inheritance are unaffected.
- **Fix:** `PS1=$'%{\e]133;B\a%}'"$PS1"` — real bytes at assignment time, no `PROMPT_SUBST`, no per-prompt subshell. Fix `docs/SHELL-INTEGRATION.md:136` identically. Add a fixture that renders the prompt through a real `zsh -i` with no options set.

### HIGH — PowerShell prompt wrapper destroys `$?` before invoking the user's original prompt
- **Where:** `shell-integration/kettle.ps1:40`
- **Trigger:** `$code = $LASTEXITCODE` (:40) and `[Console]::Write(...)` (:46) run before `& $global:__kettle_original_prompt` (:70). On Windows this is not opt-in: `crates/kettle-core/src/term.rs:3002` embeds the file and injects it via `-NoExit -EncodedCommand` for default pwsh/powershell panes, with `shell-integration = on` the default.
- **Wrong outcome:** starship/oh-my-posh capture `$origDollarQuestion = $global:?` as their first statement; with kettle's wrapper in front they always read `True`, so a failed command renders a success prompt. Verified on pwsh 7.6.4 with a control run: the wrapper alone preserves `$?`; the pre-line-70 statements are what flip it. On PS 7.2+ this covers **native** failures too, not just cmdlet errors — so under starship every failed command reports success. (On Windows PowerShell 5.1 the loss narrows to cmdlet/script errors.) `docs/SHELL-INTEGRATION.md:28-32` explicitly promises starship/oh-my-posh are left intact. `kettle.bash:35-42` documents finding and fixing this exact bug for bash.
- **Fix:** Invoke the user's prompt first, then emit D/A/OSC 7 and append B to the returned string. This also fixes a second bug the comment at :74-77 already claims but `return $rendered` (:78) contradicts — B currently lands at the same position as A.

### MEDIUM (filed HIGH) — bash OSC 7 encoder emits 16-hex-digit percent escapes on bash 3.2
- **Where:** `shell-integration/kettle.bash:30`
- **Trigger:** `printf -v ch '%%%02X' "'$ch"` on any byte ≥ 0x80 under `/bin/bash` 3.2 (what macOS ships; the file's own comment at :56-60 names 3.2 as a supported target). bash 3.2 sign-extends the `'X` value, so 0xC3 formats as `FFFFFFFFFFFFFFC3`. Reproduced on 3.2.57: cwd `/tmp/kt test/ünïcode` emits `%FFFFFFFFFFFFFFC3%FFFFFFFFFFFFFFBCn…`; Homebrew bash 5.3 is correct.
- **Wrong outcome:** `parse_osc7_with_host` (`crates/kettle-vt/src/extract.rs:1242-1268`) consumes `%FF` as byte 0xFF and passes the remaining hex through as literal text; `safe_reported_cwd` accepts the result (POSIX-absolute, no control chars) and stores it as authoritative. Residual damage: `Action::OpenCwdInFileManager` (`app.rs:13918`) opens nothing, the cwd-derived tab label shows visible garbage, and new-pane cwd inheritance is lost. It does **not** spawn into a nonexistent dir — `usable_cwd` (`crates/kettle-ui/src/mux.rs:3899-3901`) `is_dir`-filters the candidate and falls back.
- **Fix:** Mask to a byte: `printf -v ch '%%%02X' "$(( $(printf '%d' "'$ch") & 0xFF ))"`. Add a fixture that runs the encoder under `/bin/bash` on macOS CI with a non-ASCII path and asserts a three-character escape — a bash-5-only test cannot fail.

### MEDIUM (filed HIGH) — zsh snippet defines `precmd`/`preexec` outright, deleting the user's existing hooks
- **Where:** `shell-integration/kettle.zsh:36-37`
- **Trigger:** A `~/.zshrc` that hand-defines `precmd`/`preexec` (zsh's own `vcs_info` docs tell you to), followed by the appended kettle block. Reproduced: with `precmd() { print -n "USER-PRECMD-RAN " }` defined first, `whence -f precmd` afterwards shows kettle's body only.
- **Wrong outcome:** The user's hooks are destroyed with no diagnostic — `vcs_info` stops updating, titles stop changing. Reverse ordering is equally broken. **Scope narrowed by verification:** frameworks that use `add-zsh-hook` (starship, oh-my-zsh, powerlevel10k, prezto, kitty/iTerm2 integrations) are provably unaffected — zsh runs both the `precmd` function and every `precmd_functions` entry. Affected population is hand-rolled configs. The sibling files handle this carefully: `kettle.bash:49-64` preserves `PROMPT_COMMAND` including the 5.1 array form; `kettle.ps1:37` stashes the user's `prompt`.
- **Fix:** `autoload -Uz add-zsh-hook; add-zsh-hook precmd __kettle_precmd; add-zsh-hook preexec __kettle_preexec` with bodies in uniquely-named functions. Also re-source safe.

### MEDIUM — PowerShell snippet unconditionally replaces the user's Enter key handler
- **Where:** `shell-integration/kettle.ps1:87`
- **Trigger:** `Set-PSReadLineKeyHandler -Key Enter -ScriptBlock {...}` with no check for an existing binding. The only wrapping conditions are a PSReadLine availability check and the `__kettle_prompt_installed` idempotency flag. `term.rs:2986-3031` loads the user's `$PROFILE` first, then kettle's hook, so kettle always wins on default Windows panes.
- **Wrong outcome:** Any Enter binding a user or module installed is silently discarded and plain `AcceptLine` runs. The concrete loss is `ValidateAndAcceptLine`'s **pre-submission parse-error gate** (stock `AcceptLine` already continues incomplete input), plus Enter bindings from history/completion modules. Contradicts the non-clobbering promise in the file header (:5-7), `docs/SHELL-INTEGRATION.md:28-32`, and CHANGELOG. Untouched profiles are unaffected (stock Enter is `AcceptLine`).
- **Fix:** Read `Get-PSReadLineKeyHandler -Bound` first; chain to the captured function after writing OSC 133;C, mirroring the stash-and-forward already done for `prompt` at :37. (PSReadLine cannot return a previously registered ScriptBlock, so at minimum detect-and-skip or warn.)

## ci

### HIGH — the "Reject mutable action references" gate has never executed
- **Where:** `.github/workflows/actionlint.yml:58`
- **Trigger:** `rg` is not in the `ubuntu-24.04` image and nothing installs it. Because the command is the `if` condition, bash exit 127 reads as "no matches" and `set -euo pipefail` (:56) cannot fire. Confirmed live: run 31149849904 logs `rg: command not found` at 2026-08-07T05:12:52Z with conclusion `success`; three more sampled runs identical; `git log -S` shows the line unchanged since it was introduced as a hardening measure.
- **Wrong outcome:** The sole enforcement of the repo's SHA-pinning policy is a no-op reporting success on every run. actionlint has no immutable-ref rule, so `uses: some/action@v4` or `@main` can land with a green `lint workflows` check while the file header (:10-11) advertises the protection. No unpinned ref exists today — discipline, not enforcement, is holding.
- **Fix:** Use a tool the image has and separate "no match" from "tool failed": `grep -rPn "$pattern" .github/workflows; status=$?; if [ "$status" -eq 0 ]; then …exit 1; elif [ "$status" -ne 1 ]; then …exit 1; fi`. Same treatment for the actionlint step at :75 — actionlint silently skips its shellcheck integration when `shellcheck` is absent from PATH.

### MEDIUM (filed HIGH) — the daily `Audit` cron cannot fail
- **Where:** `.github/workflows/audit.yml:112-124`
- **Trigger:** The 06:00 UTC schedule fires and `cargo audit` finds a vulnerability. At the pinned SHA `rustsec/audit-check@69366f33`, both `src/main.ts` and the executed `dist/index.js` branch on `eventName == 'schedule'` and call `reportIssues` instead of `reportCheck`. `reportIssues` (reporter.ts:255-327) never throws, so `core.setFailed` is never reached. The `push` leg is fine. Separately, `getStats` counts a finding as `critical` only when `advisory.informational === null`, so unmaintained/unsound/yanked never fail either leg.
- **Wrong outcome:** The header (:1-9) promises "a newly-published vulnerability … surfaces as a CI failure within a day" and names the cron as the mechanism; that window is exactly the case that cannot fail. README's Audit badge stays green. `deny.yml` explicitly delegates advisories here and is weekly, so nothing else covers advisories continuously. `dependabot.yml:43-44,53` cite `cargo audit` as the sole justification for pinning `sysinfo` and `objc2` indefinitely. The workflow's own comment at :99-100 states the branch backwards, so this was not a knowing trade-off. **Mitigations found in verification:** an issue *is* filed within a day (`alreadyReported` is title-scoped, so a fresh advisory is not suppressed), and Dependabot's weekly lock-touching PRs restore hard-fail coverage in ~a week.
- **Fix:** Give the cron its own step running `cargo audit --deny warnings` directly (the PR job at :59-64 already has that shape), or keep the action for issue-filing and add a following CLI step that fails the job.

### MEDIUM (filed HIGH) — a failing `cargo test -p portable-pty` is masked by the trailing `cargo clippy` in the same pwsh step
- **Where:** `.github/workflows/ci.yml:69-76` (test at :75, clippy at :76)
- **Trigger:** The step has no `shell:` key, so on `windows-latest` it runs under GitHub's pwsh wrapper (`$ErrorActionPreference='stop'` + `exit $LASTEXITCODE`). Reproduced on pwsh 7.6.4: a native command exiting 3 does not terminate the script and the step exits with the *last* command's code. `$PSNativeCommandUseErrorActionPreference` is `False` by default. Every Windows-running neighbour sets `shell:` explicitly (`bash` at :138/:168/:645, `pwsh` at :219/:235/:265) — this step alone falls through.
- **Wrong outcome:** `build (windows-latest)` is a branch-protection-required check (confirmed via the API), so a masked failure merges green. **Scope narrowed:** the unmasked `cargo test --workspace` at :57 covers the ConPTY writer regression class via `exec_timeout_closes_a_saturated_conpty_after_a_query` and `windows_pipe_nowait_never_blocks_at_capacity` (`crates/kettle/tests/exec.rs:1076,1255`). What is uniquely lost is the vendor package's own `WouldBlock`/recovery assertion (`vendor/portable-pty-0.9.0/src/win/conpty.rs:194`) plus the Windows half of that package's doctests. `release.yml:181` is a single command and fails correctly at tag time. `ci.yml:260-263` documents this exact pwsh trap and works around it for the GPU-smokes step 190 lines later.
- **Fix:** Add `shell: bash` to the step, or split :75 and :76 into separate steps. Same shape at `ci.yml:105-108`.

### LOW — `ci.yml` builds and tests the root workspace without `--locked`
- **Where:** `.github/workflows/ci.yml:55-57` (also `:713-714` msrv, `:746-747` nightly)
- **Trigger:** A PR edits a dependency requirement without committing the regenerated `Cargo.lock`. The vendored-crate steps immediately below (:65-68, :75-76) and every `release.yml` cargo line do pass `--locked`. No `--frozen`/`--offline`/`git diff --exit-code` freshness guard exists anywhere, and the local `gauntlet` recipe has the same gap.
- **Wrong outcome:** The three required `build (*)` checks and required `msrv` go green against a re-resolved graph that is not the committed lock, while `cargo audit` scans the committed one. (Correction to the filed claim: `cargo-deny` resolves via `cargo metadata` and would itself re-resolve, so the divergence is between `cargo audit` and the build jobs, not both supply-chain gates.) `nix.yml` catches the drift only when the new requirement is unsatisfiable from the vendored set, and Nix is not a required check. `scripts/test-update-manifest.py:214-220` asserts every `release.yml` cargo line carries `--locked`, so the policy is conscious and test-enforced — just not extended to `ci.yml`.
- **Fix:** Add `--locked` to :55, :56, :57, :713, :714, :746, :747, and to the `gauntlet` recipe.

### LOW — the release-time flake.nix version gate silently passes when its awk pattern matches nothing
- **Where:** `.github/workflows/release.yml:91-98`
- **Trigger:** `FLAKE_VER=$(awk -F\" '/^          version = / { print $2; exit }' flake.nix)` depends on exactly 10 leading spaces (`flake.nix:114`, verified). A manual reindent or restructure makes awk match nothing, and the `[ -n "$FLAKE_VER" ] &&` guard on :92 skips the comparison. (Correction: there is no `nix fmt` in this repo — no `formatter` output exists — so the trigger is a hand edit, not a formatter pass.)
- **Wrong outcome:** :98 prints "tag, Cargo.toml, flake.nix, and CHANGELOG.md all agree" unconditionally while flake.nix carries a stale version. Blast radius is the Nix derivation's `version` metadata only (archives, manifest, Homebrew, PKGBUILD all derive from the tag/Cargo.toml). `scripts/release.sh:216-219` records that this drift already happened silently for 39 releases. The sanctioned path is protected (`replace_first_line` fails loudly on the same shape); the silent path is a hand-cut tag, which :94 explicitly contemplates.
- **Fix:** `if [ -z "$FLAKE_VER" ]; then echo '::error::could not extract a version from flake.nix'; exit 1; fi`, and loosen the pattern to `/^[[:space:]]*version = "/`.

## uiux-design

### HIGH — Settings number rows snap an out-of-range config value to the row's own range on the first arrow press, in either direction
- **Where:** `crates/kettle-ui/src/settings.rs:497-511` (`next_value` Number arm); rows at `:282-283`, `:209`, `:292-299`
- **Trigger:** `scrollback = 500000` (valid; the parser clamps only at 10 M, `kettle-config/src/lib.rs:4149`). Open Settings → Behavior, highlight "Scrollback lines" (correctly shows `500000`), press → **or** ←.
- **Wrong outcome:** `(500000 ± 1000).clamp(0, 100_000)` = 100000, and `settings_adjust` (`app.rs:18406-18528`) persists it at :18490 and calls `reload_config`. `apply_reloaded_config` → `set_scrollback_limits` (`kettle-core/src/term.rs:5662-5687`) deliberately honors a *decrease* by discarding the oldest rows "immediately and irreversibly" — so one keypress rewrites the config and destructively trims live pane history. Same shape on every row whose config range exceeds the row's: `background-opacity = 0.10` → ← *raises* it to 0.20; `update-check-interval-hours = 8760` → 720; `scrollback-bytes = 4G` → 1024 MB. This is the unfixed remainder of the fix at `settings.rs:719-732`, which special-cased only `scrollback >= INFINITE_SCROLLBACK`; both existing tests (`:766`, `number_steps_and_clamps` `:1069`) drive only in-range values.
- **Fix:** Clamp the *step*, not the current value — when `cur` is outside `[min, max]`, return `cur` unchanged or step one increment toward the range. Add `cur > max` / `cur < min` cases to `number_steps_and_clamps` and cover the opacity, scrollback-bytes and update-interval rows.

### MEDIUM — a Settings keybind rebind that cannot be written reports nothing, while every other Settings row notifies
- **Where:** `crates/kettle-ui/src/app.rs:18190-18220` (`apply_keybind_rebind`)
- **Trigger (corrected — the filed repro does not reproduce):** `chmod 444` on the config *file* does **not** fail; `ConfigEdit::commit` writes via `kettle_state::atomic_replace` (staged temp + rename), which needs only a writable parent. Reachable triggers: read-only **parent directory** (measured `PermissionDenied`), no resolvable config path (the whole `if let Some(path)` body is skipped with not even a log), non-UTF-8 config (`InvalidData`), path not a regular file, disk full.
- **Wrong outcome:** The live keymap is mutated first, `append_keybind` failure is only `log::warn!`ed (:18212-18218), and the overlay redraws from the live map showing the new chord as bound. The rebind is gone next launch. Every sibling write surfaces failure as a desktop notification — general row :18490-18495, GPU :18477-18484, padding mirror :18506-18512, inline text prompt :18565-18571 — and `persist_pref` even returns false specifically so callers can notify. Both entry points (:18308 direct, :14408 conflict-confirm) converge here. `docs/SETTINGS.md:123` tells the user it "is saved to your config". `docs/AUDIT-DEFERRED.md:70` closed only the conflict-warning half.
- **Fix:** Return the write outcome (including the no-path case) and `fire_notify("kettle: keybind not saved", "Applied for this session — couldn't write it to your config file.")`, mirroring `persist_search_pref` (`app.rs:12332-12337`).

### MEDIUM — "Advanced… (open config in $EDITOR)" never consults `$EDITOR`, and reports nothing when the desktop has no handler
- **Where:** `crates/kettle-ui/src/app.rs:12788-12802` (`Action::EditConfig`)
- **Trigger:** With `EDITOR=nvim`, right-click → Preferences ▸ "Advanced… (open config in $EDITOR)" (`app.rs:11125`) or the palette entry (`kettle-config/src/palette.rs:36`). Both converge on the single arm, which calls `open::that_detached(&path)` and nothing else. No `env::var("EDITOR")`/`"VISUAL"` read exists anywhere in the UI dispatch path.
- **Wrong outcome:** Dispatch goes to the desktop file association. `~/.config/kettle/config` has no extension, so on a plain WM without a `text/plain` association nothing opens — and per `open` 5.4.0's `that_detached` (lib.rs:278-291), success is returned as soon as the first launcher *spawns*, so when `xdg-open` exists but has no association not even the `log::warn!` fires. Where an association exists the file opens in a GUI editor or Windows' "How do you want to open this file?" picker. The `$EDITOR` promise appears in five places: `app.rs:11125`, `palette.rs:36`, `docs/SETTINGS.md:133`, `docs/CONFIG.md:396`, `docs/GETTING-STARTED.md:49`. The internal design record at `keybinds.rs:239-246` also says the path is written to the pane's PTY — the arm does no such write.
- **Fix:** Prefer `$VISUAL`/`$EDITOR` by opening a new kettle tab/pane running it on the config path; fall through to `open::that_detached` only when neither is set; `fire_notify` on failure. If OS-handler dispatch is intended, relabel all five surfaces.

### LOW (filed MEDIUM) — "Scrollback MB" renders the documented "no byte cap" as `0MB`, and one arrow press imposes a 10 MB cap
- **Where:** `crates/kettle-ui/src/settings.rs:437` (`read`), `:733` (`read_number`), `:746` (`write_number`)
- **Trigger:** `scrollback-bytes = 0` (documented as "disables the byte cap", `docs/CONFIG.md:81`; pinned by `term.rs:3504`). Settings → Behavior → "Scrollback MB" reads `0MB`; press →.
- **Wrong outcome:** The sentinel-to-word conversion is gated on `field.key == "scrollback"` only, so the bytes row with identical grammar shows a bare `0MB`, inviting the user to raise it. `next_value` yields `10MB`, which is persisted and applied downward on the spot (`app.rs:14822` → `term.rs:5662-5687`), trimming history irreversibly. The `scrollback` row was fixed for exactly this (`settings.rs:783`: a bare `0` "invited a user to step off it without realising it"); the sibling two lines below (`:283`) was left alone. Held at LOW because 0 is in range, ← is a no-op, → does exactly the requested arithmetic and repaints as `10MB`, and the config change is reversible.
- **Fix:** Render `0` as "no cap"/"unlimited" for `scrollback-bytes` and make `next_value` step deliberately off the sentinel. Extend `stepping_the_scrollback_row_cannot_silently_discard_infinite_history` to the bytes row. Note integer-MB truncation also displays any sub-1 MB cap as `0MB`.

- **Trigger:** A user reads the Default column for `title-transmit-bg-color` / `title-receive-bg-color` / `title-inactive-bg-color` and their `-fg-color` partners.

### LOW (filed MEDIUM) — CONFIG.md claims `geometry-hinting` snaps resizes to the font cell grid; the code hardcodes an 8×16 logical-pixel step
- **Where:** `docs/CONFIG.md:108`; implementation at `crates/kettle-ui/src/app.rs:20605-20607` (filed as :20351 — anchor drift)

### MEDIUM — `run_command` reports `output_truncated: false` while a hard 10,000-line cap has silently dropped the head of the output
- **Where:** `crates/kettle-ui/src/app.rs:17308-17335` (`ctl_capture_output_since`; `CAP_LINES` at :17309) — filed as :17079/:17067, anchor drift
- **Trigger:** Precondition (stated up front, priced into the severity): the pane must retain more than 10,000 lines, e.g. `scrollback = 100000` with `scrollback-bytes = 0`. Then `kettle ctl run_command --text 'seq 1 15000'` or `kettle_run_command` with OSC 133 integration. `take = hist.saturating_sub(start_line).min(CAP_LINES)` makes `first_abs > start_line`, `start_idx` saturates to 0, and the first ~5,000 lines are never in `lines`. - **Wrong outcome:** Both reply paths — `resolve_pending_run` (:17223-17238) and the timeout branch of `check_pending_run_deadlines` (:17278-17293) — return `{output, output_truncated: false}`, and that flag is the only completeness signal the contract exposes. `docs/AGENT.md:271` defines it as the truncation flag ("output is capped at 512 KiB"); `ctl_cli.rs:194-203` prints the body plus `[exit N]` and never surfaces the flag at all; the MCP tool description promises "output" with no caveat. An agent reads a body starting mid-stream — missing compile errors or failing test names — and is told the capture was complete. The 10,000-line cap is documented nowhere user-facing, and every other capped read surface in this codebase (`read_screen`'s `text_truncated`, `selection_truncated`, paged `truncated`) does report its cap.

## scripts — installers

### MEDIUM — the Windows installer's user-PATH edit expands and type-downgrades the whole `HKCU\Environment\Path`
- **Where:** `scripts/install.ps1:5132-5149` (`Invoke-KettleUserPathEdit`; read :5134, write :5147); callers at :5868 (install) and :5244 (uninstall)
- **Trigger:** A default run — the PATH update is on by default, `-NoPath` is the opt-out (`.DESCRIPTION` :26-27). The function reads with `[Environment]::GetEnvironmentVariable("Path","User")` and writes with `SetEnvironmentVariable(...,"User")`. For the User target the getter calls `RegistryKey.GetValue(name)` with `RegistryValueOptions.None` (expanding a `REG_EXPAND_SZ`) and the setter calls `SetValue(name, string)` (storing `REG_SZ`) — identical on .NET Framework (PS 5.1) and .NET 5+ (pwsh 7). The trigger does not need rustup: the stock Windows 10/11 `HKCU\Environment\Path` is itself `REG_EXPAND_SZ` containing `%USERPROFILE%\AppData\Local\Microsoft\WindowsApps`, so a plain default install on a stock machine already does this.
- **Wrong outcome:** After one run the value is a fully expanded `REG_SZ`: every `%VAR%` entry (`%JAVA_HOME%\bin`, `%GOPATH%\bin`, …) is frozen to its install-time value, so changing the variable no longer moves the entry and a moved/roamed profile leaves dead entries. Contradicts the documented uninstall contract at :31-33 ("the PATH addition (only if the entry is exactly this install dir)") — one entry is touched logically, all are rewritten physically — and uninstall (:5244) rewrites again without restoring the kind, so the script cannot undo it. Not covered by the smoke: `check-windows-installer.ps1` runs with `$IntegrationTestRoot`, which forces `$NoPath = $true` at :5108, and the uninstall-side call returns `$false` before writing, so the PATH-identity assertion at :1323 passes trivially. A repo-wide grep for `DoNotExpand|RegistryValueOptions|ExpandString|HKCU:\Environment` has one unrelated hit (`scripts/perf/lib-win32.ps1:998`).
- **Fix:** Operate on `HKCU\Environment` directly: read with `GetValue('Path', $null, [Microsoft.Win32.RegistryValueOptions]::DoNotExpandEnvironmentNames)`, remember `GetValueKind('Path')`, write back with `SetValue('Path', $new, <original kind>)` (default `ExpandString` when absent), then broadcast `WM_SETTINGCHANGE`. Keep the exact-match add/remove logic unchanged.

### LOW (filed MEDIUM) — `install.sh`'s version probe aborts the whole install with zero diagnostic
- **Where:** `scripts/install.sh:167`
- **Trigger:** `KETTLE_VERSION=$("${BIN_SRC}" --version 2>/dev/null | awk 'NR == 1 { print $2 }')` under `set -euo pipefail` (:32), as a standalone assignment with no `if`/`&&`/`||` exemption. When the binary exists and is executable but cannot run, `pipefail` propagates and `set -e` exits at that line. Reproduced end-to-end against the unmodified script with a fake tarball layout and a mode-755 garbage `kettle`: exit 126, **0 bytes on stdout and 0 bytes on stderr**, no prefix created. The `2>/dev/null` swallows bash's own exec-failure message because the redirection is installed in the child before exec. The only guard at :153 checks the executable bit, never runnability.
- **Wrong outcome:** The script exits nonzero having printed nothing — its first tarball-mode `echo` is at :202. Through `install-online.sh:826`, which captures stdout into `$INSTALL_LOG` and only `cat`s it on failure, the `curl … | sh` user sees the SHA-256/Ed25519 line and then a bare exit 1. `AGENTS.md:14-15` requires explicit failure semantics of installer paths. Separately, the `KETTLE_VERSION=${KETTLE_VERSION:-unknown}` fallback on :168 is dead *for this case* (it is still reached when the probe exits 0 with no second field), even though `unknown` is a first-class value that `install-unix.py:586` whitelists and `install.ps1:5704-5718` produces via try/catch. **LOW rather than MEDIUM:** no supported configuration is affected — `README.md:164` and `docs/INSTALL.md:7-8,46-48,77-80` declare glibc 2.35+ and route older/musl users elsewhere, and wrong-arch is excluded by `install-online.sh`'s arch-keyed asset selection — and the abort precedes any write, so no partial state.
- **Fix:** Capture stderr and tolerate a failing probe: `if ! version_output=$("${BIN_SRC}" --version 2>&1); then …warn to stderr…; version_output=''; fi` then extract and fall back to `unknown`. Decide explicitly whether an unrunnable binary should abort — if so, abort with the captured loader error rather than in silence.

## Refuted — checked and dismissed, do not re-investigate

1. **Linux installer publishes files before recording provenance; interrupted install wedges re-install and uninstall** — mechanism reproduces, but the two named triggers are misreads: `bin/kettle` is the first spec published and `_publish_source`'s `finally` unlinks before `os.replace`, so an ENOSPC during the 40 MB copy leaves a retryable empty `bin/`; deterministic mid-loop failures are already preflighted at `:697-700`. Real window is a hard fault in the sub-second tail between the binary commit and the manifest write. Residual: narrow robustness gap worth the Windows-transaction treatment, MEDIUM at most — filed as HIGH, so excluded.
2. **`install-unix.py` uninstall unlinks the manifest last, so an interrupted uninstall can never be resumed** — the stranding is caused by the fail-closed `_verify_file` preflight, not by the ordering; the proposed fix direction (unlink the manifest first) would regress into the already-fixed disowned-files bug. The described stranded state is impossible: the (depth, path) descending sort removes icons and the man page before any entry point. Residual: making uninstall tolerate ENOENT is a small legitimate hardening, LOW.
3. **aarch64-linux is a mandatory release artifact with only a `continue-on-error` debug build as pre-tag coverage** — every mechanic checks out, but the failure mode is fail-safe (nothing publishes, ~40 min lost), the non-blocking choice is stated deliberately at `ci.yml:751-753`, and it has never materialized across ~44 tagged releases with 25/25 recent runs green. Residual: the stale comment at `ci.yml:753-755` describing the shipped aarch64 artifact as a future follow-up, LOW.
4. **bash snippet's DEBUG trap clobbers an existing DEBUG trap** — the bash-preexec/Atuin trigger is mechanically impossible (bash-preexec installs its trap at first PROMPT_COMMAND, after `.bashrc` runs), and the reverse order is safe because bash-preexec captures `trap -p DEBUG` and re-registers it — verified byte-correct under bash 5.3. Missing 133;C is a documented fail-safe (`term.rs:4998-5017` errs toward asking). Residual: a `trap -p DEBUG`-preserving guard would harden against a bare hand-written trap, LOW.
